# Render resources: observable vs account-only

Verified against first-party documentation (2026-09-25). Do not interpret a container's current capacity as a monthly billing balance.

- [Render free services](https://render.com/docs/free): 750 free instance-hours **per workspace per calendar month**; only running time consumes hours. Services spin down after 15 minutes idle, and the next request can take about a minute to wake. Free instances have no persistent disk; outbound bandwidth and build minutes also count toward workspace allowances. **Actual remaining amounts belong to the authenticated Billing page**.
- [Compute plans](https://render.com/docs/compute-plans): free web-service plan is advertised as 0.1 CPU / 512 MB. The live container cgroup was previously observed reporting a 0.15-core quota / 512 MiB; these describe different surfaces, so do not equate or infer a workspace allowance from either.
- [Default environment variables](https://render.com/docs/environment-variables): `RENDER_GIT_COMMIT` identifies the running deploy's commit at runtime; service and instance IDs exist but should not be needed for public diagnostics. Git SHA alone is not the Render deploy ID.
- [Render metrics API](https://api-docs.render.com/reference/metrics): CPU, memory and bandwidth history and [deploy list](https://api-docs.render.com/reference/list-deploys) require a bearer key. [API key access](https://api-docs.render.com/reference/authentication) spans **all workspaces** for the user; the docs do not establish read-only per-service credentials. Never copy the local CLI credential to this publicly reachable app without an explicit security decision.

## What this deployment actually displays

SYSTEMS measures the **current cgroup**: CPU used as a percentage of quota over the latest sampling interval, memory used vs cgroup limit and remaining capacity; a timestamped sliding window up to 60 minutes, created on requests only; process startup time/uptime and the public Git revision `RENDER_GIT_COMMIT`; Glance page-content loads and render failures since start. Server data resets on sleep or deploy. Additionally, the visitor's browser stores up to eight public Git revisions with observed maximum CPU/memory and number of distinct snapshots captured while TODAY or SYSTEMS was visited. This local-only, optional history survives a Render deployment *in that browser*, but is neither complete usage nor a reliable deployment event log; repeating the same commit SHA groups observations together. Clearing browser site data removes it. It does **not** measure every application in the workspace, billing allowances, monthly free hours remaining, total outbound bandwidth, pipeline minutes, deploy status/history or all network errors.

Those unavailable account-level values are labeled as such and link to Render's authenticated **Billing**, **Metrics**, and **Deploys** pages. This pattern remains correct on future deployments without provisioning a broad account key or persistent monitoring service. Source freshness and render errors are validated using local scripts rather than adding a daemon.
